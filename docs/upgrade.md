# 升级

[HFile](../README.md) › [文档](README.md)

升级的做法是：停掉旧的程序，换上新的文件，再启动。新版本在开始提供网页之前先检查数据库：

1. 数据库结构和程序一致：直接启动。
2. 有数据库还没执行的迁移（Django 的 migrations）：
   1. 先把整个数据库备份到备份文件夹（默认是 `config.toml` 旁边的 `backups/`），文件名是库名（SQLite 是数据库文件的名字）、日期和要升级到的版本，例如 `hfile-20261107-231322-before-0.2.0.sql.gz`，权限 600。备份失败就不升级，程序停下。
   2. 执行迁移。
   3. 迁移出错时（MySQL 改表不能回滚；SQLite 只撤回出错的那一个迁移，前面执行过的不撤回），用刚才的备份把整个数据库恢复原样，然后停下不启动。原来的版本可以接着用。
   4. 成功后记一条升级记录：时间、从哪个版本升到哪个版本、执行了哪些迁移、备份文件在哪。管理页的「版本与升级」能看到。
3. 数据库里有程序不认识的迁移，说明它被更新的版本升级过：旧版本在新的数据库上可能出错，所以拒绝启动，并提示怎么办。
4. 数据库里是别的程序的表（没有 HFile 的迁移记录，比如 `[database] name` 写错成了别的程序的库）：不升级，什么都不改，程序停下并说明原因。
5. 连不上数据库（SQLite 是打不开数据库文件）也不启动，提示检查 `config.toml` 的 `[database]`。

`[upgrade] auto` 管第 2 步是不是自动做：不写时单文件程序是开的；从源码运行是关的，开发时新写的迁移不会被马上执行。关着时有没执行的迁移，`serve` 会停下并提示先运行 `upgrade` 命令（从源码是 `python -B manage.py upgrade`，单文件程序是 `hfile upgrade`），`runserver` 只提醒。第 3、4、5 步不管开不开都照做。

同一个数据库同时只能有一个进程在升级或恢复。MySQL 用命名锁（`GET_LOCK`）；SQLite 用数据库文件旁边的锁文件（`hfile.sqlite3.lock`），进程退出时系统自动放开，文件留着也没关系。两个进程一起启动时，只有一个升级，另一个等它升级完（最多等 10 分钟）。

自动升级开着时（还有手动 `upgrade` 时），只换了程序、数据库结构没变的版本也记一条升级记录，不用备份；全新的空数据库第一次启动就把所有表建好，这时没有可备份的东西。

命令（从源码运行时把 `hfile` 换成 `python -B manage.py`）：

| 命令 | 作用 |
|---|---|
| `hfile --version` | 程序版本 |
| `hfile upgrade --check` | 只检查要不要升级，不改数据库。退出码：0 不用升级，1 需要升级，2 数据库比程序新，3 不是 HFile 的数据库（别的程序的表），4 读不了数据库（连不上、打不开文件） |
| `hfile upgrade` | 现在就升级，步骤和启动时一样。网站在运行时拒绝（见下面的「恢复」） |
| `hfile backup [-o 文件.sql.gz]` | 随时备份整个数据库，默认放进备份文件夹 |
| `hfile restore 文件.sql.gz [--yes]` | 用备份替换整个数据库：先把现在的数据库另存一份，再删掉全部表、导入备份。会先问一遍，`--yes` 不问。要先停掉网站。备份不完整、和现在的数据库不是同一种（MySQL、SQLite）、来自更新的版本时，什么都不动就拒绝 |

退回旧版本：停掉新版本，用升级前的备份恢复（`hfile restore backups/…-before-<新版本>.sql.gz`），再启动旧版本。只换回旧文件、不恢复数据库的话，旧版本会拒绝启动；新版本只是加了新的应用（新的表）时例外：旧版本看不出数据库被升级过，会照常启动，只是不用那些表。

恢复：

- 恢复前先停掉网站。`serve` 运行时对它的设置文件拿着一把锁，`restore` 和 `upgrade` 用同一个设置文件时看得到，会拒绝并提示先停掉它；用别的方式运行的网站（gunicorn、另一台机器、另一个设置文件）看不出来，要自己先停。网站开着时恢复，网站的请求会出错，恢复完以后网站在最多 30 秒里还用着旧的设置。
- 来自更新版本的备份（里面的数据库执行过这个程序没有的迁移）不恢复：恢复了这个程序也不能用它。备份里记着它的数据库执行过哪些迁移，动数据库之前就能查出来。
- SQLite 的恢复在一个事务里，失败了数据库就是原样。MySQL 的恢复先删掉所有表、再一张一张建，建表不能回滚：中途有一条语句失败（断线、磁盘满，或者网站这时写进了一行），`restore` 就用刚才另存的那份把数据库换回去，和升级失败时一样；那一份也换不回去时，说明数据库现在不完整，要用 `restore` 恢复哪个文件。

备份：

- 程序自己用 Python 写备份，单文件程序不需要 mysqldump，也不需要 sqlite3 程序。两种数据库的备份格式一样：gzip 压缩的 SQL，开头几行写着程序版本、数据库的版本、数据库类型（`-- 数据库类型：MySQL` 或 `SQLite`）和库名，最后一行是「备份结束」。
- MySQL 的所有表在同一个 InnoDB 快照里读出（REPEATABLE READ），网站运行时备份也是一致的；SQLite 在一个读事务里读出（WAL 模式下网站照常写入）。
- 备份先写成临时文件（独占创建，同一秒开始的两个备份不会写进同一个文件），写完、落盘后才改名；文件权限 600，新建的备份文件夹 700。里面有密码哈希，只给文件主人读。旧备份不会自动删除；备份被打断（`kill -9`、断电）时留下的临时文件 `.sql.gz.part`，一天没动过的由 `hfile cleanup` 删掉（见[「运行」](deploy.md)）。
- 恢复前先把整个文件读一遍，不完整的备份不会删任何表。恢复只执行备份里会有的语句，别人给的备份文件也不能借机做别的事：SQLite 上不许 `ATTACH`、`PRAGMA` 和结束事务，整个恢复在一个事务里，要么全换掉、要么什么都不变；MySQL 上先把整个文件查一遍，只能是 `DROP TABLE IF EXISTS`、`CREATE TABLE`、`INSERT INTO` 和备份开头结尾那几句固定的 `SET`，有别的就一张表也不删、直接拒绝。一行超过 64 MB 的也不读。
- 不用这个程序也能恢复：MySQL 是 `gunzip -c 备份.sql.gz | mysql -u 用户名 -p 数据库名`；SQLite 恢复成一个新文件，`gunzip -c 备份.sql.gz | sqlite3 新的数据库文件`，再让 `[database] file` 指向它。

发布新版本时：

- 每次发布都改 `config/version.py` 的 `VERSION`，标签是 `v` 加版本号，发布流程会核对（见[打包](build.md#发布)）。要不要升级数据库只看迁移，和版本号无关；版本号用在升级记录和提示里，版本变了而没有新迁移时，升级记录里也记一行。
- 已经发布的迁移不再修改，有问题就加一个新迁移。0.1.0 是第一次发布，它的 29 个迁移从此固定下来。0.2.0 加了 `links.0002`（下载日志的「页面下载」和用户名）。1.0.0 加了 `siteconf.0002`、`storages.0002`（代理下载的连接数和速度限制）。
- 每个迁移都要能在已有的数据上跑通（比如加唯一约束之前先处理重复数据）。万一跑不通，用户那边会自动恢复，但这个版本就用不了了。
